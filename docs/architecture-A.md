# Task Tracker Architecture

## 1. What the app does

Task Tracker is an educational Kanban-style web app for creating, viewing, filtering, updating, moving, and deleting tasks across `ToDo`, `InProgress`, and `Done` columns. It consists of a FastAPI JSON API and a separately served, single-file vanilla HTML/CSS/JavaScript frontend.

## 2. Data model

The sole active entity is **Task**:

- `id`: generated UUID string.
- `title`: required, trimmed, nonblank, maximum 200 characters.
- `description`: string; defaults to `""`, including when creation receives `null`.
- `due_date`: optional date serialized as `YYYY-MM-DD`.
- `status`: `ToDo`, `InProgress`, or `Done`; defaults to `ToDo`.
- `priority`: `Low`, `Medium`, or `High`; defaults to `Medium`.
- `assignee`: optional string.
- `created_at`, `updated_at`: UTC timestamps generated by the backend.

Pydantic provides separate creation, partial-update, and response models.

## 3. Request flow

When a user submits the create-task modal, frontend JavaScript trims the title and assignee, builds a JSON payload, and sends `POST http://localhost:8000/tasks`. FastAPI parses and validates it as `TaskCreate`; invalid or unknown fields produce HTTP 422. The route passes valid data to `storage.add_task`, which generates the UUID and UTC timestamps, applies storage normalization, inserts a `TaskResponse` into the process-local dictionary, and returns it with HTTP 201. The frontend then closes the modal and reloads the board through `GET /tasks`.

## 4. Key files

- `app/main.py` — FastAPI initialization, CORS configuration, health check, and CRUD route handlers.
- `app/models.py` — Pydantic request/response models, enums, defaults, and title validation.
- `app/storage.py` — In-memory CRUD operations and combined task filtering.
- `app/business_rules.py` — Allowed task-status transitions and transition errors.
- `app/frontend/index.html` — Complete static UI, API calls, rendering, filtering, modal editing, and drag-and-drop.
- `tests/test_tasks.py` — API behavior and validation tests.
- `tests/conftest.py` — Test client and automatic storage-reset fixtures.
- `README.md` — Setup, runtime architecture, conventions, and limitations.
- `docs/midcourse/mini-adr.md` — Design rationale for due dates, overdue detection, search, and filters.

## 5. Conventions

- **Validation:** Pydantic rejects invalid enum/date values and unknown fields with HTTP 422. Titles are trimmed and must contain 1–200 characters.
- **Updates:** `PATCH` applies only explicitly supplied fields. An empty patch is a successful no-op; status changes must follow the one-step transition rules.
- **Storage:** Tasks are held in an insertion-ordered Python dictionary. Data is lost whenever the backend process restarts.
- **Errors:** Missing task IDs return HTTP 404; invalid transitions return HTTP 422; successful deletion returns HTTP 204 with no body.
- **Filtering:** Active `status`, `priority`, `overdue`, `assignee`, and `search` filters use AND logic. Overdue uses the backend’s local date and excludes completed tasks.
- **Frontend/backend interaction:** The frontend is served separately, calls a hardcoded `http://localhost:8000`, and relies on the backend’s CORS allow-list. Status-transition rules are duplicated in frontend JavaScript and must remain synchronized with the backend.

## 6. Not visible or assumptions

No database, authentication, authorization, user accounts, environment-based configuration, or production deployment is implemented. Ownership semantics for `assignee`, persistence guarantees, multi-process consistency, and user-timezone handling are not defined. Unused legacy task classes in `app/main.py` are not part of the active request path.
