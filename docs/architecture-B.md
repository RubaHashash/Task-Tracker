# Task Tracker Architecture

## 1. What the app does

Task Tracker is an educational Kanban-style application for creating, viewing, filtering, updating, moving, and deleting tasks. It consists of a FastAPI JSON API and a separately served vanilla HTML/CSS/JavaScript frontend. Tasks are kept only in backend memory and are lost whenever the backend restarts.

## 2. Data model

The central entity is `Task`, represented by separate Pydantic models for creation, partial updates, and responses.

- `id`: generated UUID string.
- `title`: required, trimmed, nonblank, maximum 200 characters.
- `description`: optional; defaults to an empty string.
- `due_date`: optional date serialized as `YYYY-MM-DD`.
- `status`: `ToDo`, `InProgress`, or `Done`; defaults to `ToDo`.
- `priority`: `Low`, `Medium`, or `High`; defaults to `Medium`.
- `assignee`: optional string.
- `created_at`, `updated_at`: UTC timestamps generated by the backend.

## 3. Request flow

When a user creates a task, the browser collects the form fields and sends JSON in a `POST /tasks` request to the FastAPI backend at `http://localhost:8000`. FastAPI parses the body as `TaskCreate`; Pydantic applies defaults, trims and validates the title, validates enum and date values, and rejects unknown fields. The route then calls `storage.add_task`, which generates a UUID and UTC timestamps, converts a null description to an empty string, constructs a `TaskResponse`, and stores it in the in-memory task dictionary. The API returns the complete task with HTTP 201, after which the frontend reloads and renders the Kanban board.

## 4. Key files

- `app/main.py` — Creates the FastAPI application, configures CORS, and defines health and task CRUD routes.
- `app/models.py` — Defines task status and priority enums plus create, update, and response schemas.
- `app/storage.py` — Owns the in-memory dictionary and implements task CRUD and filtering.
- `app/business_rules.py` — Enforces permitted one-step status transitions.
- `app/frontend/index.html` — Contains the complete static UI, API calls, rendering, filtering, and client-side transition rules.
- `tests/test_tasks.py` — Tests task creation, retrieval, filtering, partial updates, transitions, deletion, and validation.
- `tests/conftest.py` — Provides the FastAPI test client and resets in-memory storage between tests.
- `docs/midcourse/mini-adr.md` — Records the design decision for due dates, overdue detection, search, and combined filters.
- `README.md` — Documents setup, runtime separation, architecture, and current limitations.

## 5. Conventions

- Pydantic rejects invalid enums, invalid dates, blank or oversized titles, and unknown request fields with HTTP 422.
- Missing task IDs return HTTP 404; successful deletion returns HTTP 204 with no body.
- `PATCH` changes only explicitly supplied fields. An empty body is a successful no-op and does not change `updated_at`.
- Status changes must follow `ToDo ↔ InProgress ↔ Done`; direct `ToDo ↔ Done` and same-status transitions are rejected.
- Tasks are stored in an insertion-ordered, process-local dictionary with no database or persistence.
- List filters use AND logic. Search is a case-insensitive title/description substring match; assignee matching is trimmed, case-insensitive, and exact.
- A task is overdue only when its due date is before the backend’s current local date and its status is not `Done`.
- The frontend and backend run separately. The frontend calls the hardcoded backend URL through `fetch`, while CORS permits documented local frontend origins.
- Status-transition rules exist in both backend Python and frontend JavaScript and must remain synchronized.
