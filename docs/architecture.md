# Architecture Context Strategy Comparison

## Strategy comparison

| Strategy | What it got right | What it got wrong, missed, or invented | Best-suited task shape |
|---|---|---|---|
| **A — Minimal context** | Produced a complete architecture narrative covering the application purpose, models, create-task flow, key files, validation, updates, storage, errors, filtering, and frontend/backend interaction. It also supplied a detailed inspection list and explicitly separated active task models from legacy classes. | Despite being labeled minimal context, it makes the broadest set of repository-wide claims and says that no behavior was inferred beyond repository evidence. That breadth depended on inspecting documentation, backend code, frontend code, tests, dependencies, Docker, and CI, so the output does not demonstrate what minimal context alone can achieve. Its “Not visible or assumptions” section also states several absences as confirmed implementation facts. | Repository-wide synthesis when direct inspection is allowed and the main risk is missing an important component. It is not a clean example of a genuinely minimal-context strategy. |
| **B — Structured context** | Produced a concise system-level account spanning the API, storage, frontend, tests, conventions, status transitions, filters, overdue rules, and limitations. It identifies `AGENTS.md` as the behavior contract and marks the legacy-code rationale and dependency usage as unconfirmed. | The requested per-file summaries were absent, so it supplemented the structured context with repository inspection. Consequently, its result cannot isolate the value of `AGENTS.md` and summaries alone. Full browser behavior also remained incompletely confirmed by automated UI tests. | Broad documentation tasks that must align many behavioral rules across layers, especially when a maintained context file provides an authoritative contract. |
| **C — Targeted context** | Stayed closely tied to the three anchor files and clearly listed both the inspected and uninspected areas. It described the API models, POST flow, in-memory storage, partial updates, validation, errors, and CORS while repeatedly marking uncertainty. | It missed the implemented status-transition policy, frontend behavior, tests, documented operating assumptions, dependencies, and possible documentation/implementation/test discrepancies. Naming `app/business_rules.py` without reading it identifies a dependency but cannot document its rules. The resulting draft is too narrow for a final system-wide architecture document. | Focused request-flow or component documentation where the relevant implementation path is known and traceability matters more than whole-system coverage. |

## Verdict

I chose **Strategy B** for the final architecture document because it offered the best balance between system-wide coverage and a concise, explicit behavior contract. Strategy A was comprehensive but did not remain meaningfully minimal, while Strategy C was disciplined about uncertainty but omitted architecture-critical frontend, business-rule, test, and documentation evidence. Before finalizing B, unsupported details should remain qualified and important claims should be traceable to the files that confirm them.

## Context-engineering rule

For a system-wide architecture document that must align backend behavior, frontend behavior, tests, and documented rules, I use **structured context** because it supplies a reusable contract while preserving broad coverage. For a narrowly bounded endpoint or component flow, I use **targeted anchor files** because they keep claims traceable and make uninspected areas explicit.
